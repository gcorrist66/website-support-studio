# WSS Architecture

## 1) Project Separation and Dependency Model

WSS is a **standalone project**.

- WSS is not Website Operations Desk.
- WSS is not IntrynSync.
- WSS is not HiveRunner.

WSS uses:
- **HiveRunner** for execution concerns (workflow orchestration, task execution controls, delivery mechanics).
- **IntrynSync** for governance concerns (policy enforcement, audit events, approval evidence, compliance-oriented controls).

These two systems are integration dependencies, not replacement implementations.

## 2) Foundational Domain Hierarchy

The canonical domain hierarchy is:

**Agency → Client → Site → Ticket**

- **Agency**: The owning business entity.
- **Client**: A contracted customer under an agency.
- **Site**: A website/program surface the client owns.
- **Ticket**: The unit of support work generated by customer requests.

This hierarchy is the tenant boundary model and will support eventual multi-tenant SaaS growth.

## 3) Logical Architecture Layers

1. **Tenant/Domain Layer**
   - Agency namespace
   - Client registry under each Agency
   - Site records and associations
   - Ticket identity and lifecycle labels

2. **Workflow Layer**
   - Intake abstraction
   - Intake-to-ticket promotion rules (Phase 1 logic only)
   - Role-based handoff model (CS Agent → Gary approval)

3. **Governance Layer (IntrynSync interface)**
   - Policy checks for phase boundaries
   - Approval and audit trail requirements
   - Escalation and exception annotation rules

4. **Execution Layer (HiveRunner interface)**
   - Task execution sequencing
   - Notification and communication triggers
   - Operational handoff handshakes

## 4) Phase 1 MMVP Workflow

1. Customer submits support request
2. Ticket created
3. CS Agent triages
4. Gary approves response
5. Customer receives response
6. Ticket closes

## 5) Workflow Governance Model

Adopt a **Human-in-the-loop deterministic workflow** for Phase 1:

- strict step-by-step approvals
- no autonomous replies
- mandatory Gary approval gate
- deterministic state transitions

### Phase 1 Status Model

- `received` — customer request entered and ticket materialized
- `triaged` — CS Agent reviewed and categorized the request
- `reply_drafted` — draft response prepared
- `awaiting_gary_approval` — draft is pending Gary review
- `approved_to_send` — Gary approved outbound response
- `sent_to_customer` — final response delivered to customer
- `closed` — ticket intentionally completed
- `blocked` — ticket cannot progress without additional input

### Phase 1 Role Definitions

- **Agency Admin**: Owns enterprise-level policy and tenant access posture.
- **Client Admin**: Represents the client organization for administrative review and escalation.
- **Site User**: Customer contact associated with a specific site; may submit requests.
- **CS Agent**: Triage and prepare response drafts; owns operational quality of draft content.
- **Gary / Human Approver**: Mandatory approver before any customer-facing response is sent.
- **System**: Execution infrastructure in HiveRunner that tracks transitions and retains evidence metadata.

### Phase 1 Exception Handling

- **missing customer email**: pause to source contact method before progressing beyond `awaiting_gary_approval`.
- **unclear ticket type**: CS Agent flags as `blocked`, requests clarification, then resumes on receipt.
- **urgent production issue**: mark with elevated priority, route through expedited response path, retain deterministic approvals.
- **duplicate ticket**: consolidate under earliest open ticket and mark subsequent duplicate as blocked/linked.
- **sensitive/private data submitted**: block response drafting until data handling check passes.
- **request belongs to wrong site/client**: re-route or return clarification request before processing.

### Phase 1 Governance Evidence Requirements

- ticket source
- submitter identity if known
- site of origin
- timestamp
- customer message
- classification
- drafted reply
- approval decision
- sent confirmation
- closure note

## 6) Scope Boundaries

### In Scope (Phase 1)
- Tenant hierarchy definition
- MMVP support request-to-close workflow
- Human-centered approval gate model
- Governance-aligned documentation and decision checkpoints

### Out of Scope (Phase 1)
- Dev Agent
- IntrynSync integration
- Learning capture
- Feature voting
- Customer dashboards
- Autonomous replies
